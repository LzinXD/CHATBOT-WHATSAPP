Quero que você faça uma reestruturação completa do chatbot do projeto PortMind AI para a NOVA versão do produto.

IMPORTANTE:
Antes de alterar qualquer código, analise a estrutura atual do projeto, os arquivos existentes, a arquitetura em TypeScript, as rotas, controllers, services e integrações já implementadas.

NÃO recrie o projeto do zero.
NÃO remova funcionalidades existentes sem justificar.
NÃO altere arquivos fora do escopo sem necessidade.
NÃO invente integrações ou APIs que ainda não existem.
Primeiro analise o código atual e depois proponha/execute a alteração.

==================================================
1. CONTEXTO ATUAL DO PORTMIND AI
==================================================

O PortMind AI foi reposicionado.

A versão antiga era baseada principalmente em:
câmeras → Visão Computacional → detecção de vazamento.

Essa não é mais a concepção principal.

A nova solução utiliza prioritariamente os sensores de pressão já existentes nas tubulações.

O conceito agora é:

Sensores de pressão
→ coleta de dados
→ análise do comportamento dos sensores
→ identificação de possível anomalia
→ indicação de trecho provável/prioritário
→ geração de alerta
→ WhatsApp
→ validação humana
→ confirmação ou rejeição
→ atualização da ocorrência
→ armazenamento do resultado.

A IA/software NÃO deve afirmar que existe um vazamento com certeza.

Ela deve indicar:

"Possível vazamento"
ou
"Possível anomalia"

e apresentar o trecho provável/prioritário para inspeção.

Nunca utilizar "localização exata" como regra do sistema.

==================================================
2. OBJETIVO DO CHATBOT
==================================================

O chatbot do WhatsApp não será o responsável pela detecção.

A detecção acontece no PortMind AI.

O chatbot será responsável principalmente por:

1. Receber o alerta gerado pelo PortMind.
2. Apresentar ao responsável as informações da ocorrência.
3. Perguntar se a suspeita estava correta.
4. Solicitar uma confirmação humana.
5. Permitir CONFIRMAR ou REJEITAR.
6. Enviar essa decisão de volta ao backend.
7. Atualizar o estado da ocorrência.
8. Registrar a decisão para histórico.
9. Posteriormente permitir consulta de ocorrências, caso essa funcionalidade seja mantida.

==================================================
3. NOVO FLUXO PRINCIPAL DO CHATBOT
==================================================

O fluxo principal deverá ser iniciado pelo sistema, e não necessariamente pelo usuário.

Exemplo:

O PortMind identifica uma possível anomalia:

Duto: D02
Trecho provável: D-E
Horário: 15:42
Sensores envolvidos: D e E

O sistema deve gerar uma mensagem como:

"🚨 PORTMIND AI — POSSÍVEL ANOMALIA

Foi identificada uma possível anomalia na tubulação.

Duto: D02
Trecho provável: D–E
Horário: 15:42

Verifique a situação no local.

A detecção estava correta?

[ CONFIRMAR ]
[ REJEITAR ]"

==================================================
4. PERGUNTA DE CONFIRMAÇÃO
==================================================

Essa é uma mudança obrigatória.

Depois de apresentar a possível ocorrência, o bot deve perguntar explicitamente ao usuário:

"A detecção estava correta?"

O usuário deve poder responder:

1 - CONFIRMAR
2 - REJEITAR

Também deve ser possível aceitar textos equivalentes, por exemplo:

"confirmar"
"sim"
"correto"
"rejeitar"
"não"
"falso positivo"

Se possível, normalizar essas respostas.

==================================================
5. ESTADO DA CONVERSA
==================================================

O chatbot deve utilizar estado por usuário.

Exemplo:

Estado inicial:
IDLE

Quando um alerta for enviado:
AGUARDANDO_VALIDACAO

Se o usuário confirmar:
CONFIRMADO

Se o usuário rejeitar:
REJEITADO

Depois da resposta:
retornar para IDLE

O estado deve estar associado ao identificador do usuário/telefone.

NÃO utilizar usuário fixo como "teste" na lógica definitiva.

A implementação deve estar preparada para futuramente utilizar o número real do WhatsApp como identificador.

==================================================
6. EXEMPLO DE FLUXO
==================================================

Sistema:

"🚨 PORTMIND AI — POSSÍVEL ANOMALIA

Duto: D02
Trecho provável: D–E
Horário: 15:42

Verifique a situação no local.

A detecção estava correta?

1 - Confirmar
2 - Rejeitar"

Usuário:

1

Bot:

status_da_ocorrencia = CONFIRMADA
validacao_humana = CONFIRMADA

Usuário:

2

"Ocorrência rejeitada.

A rejeição foi registrada no sistema."

Backend deve registrar:

status_da_ocorrencia = REJEITADA
validacao_humana = REJEITADA

==================================================
7. TELEMETRIA X OCORRÊNCIA
==================================================

É obrigatório separar esses dois conceitos.

ESTADO DA TELEMETRIA:

Representa o comportamento dos sensores.

Exemplos:

NORMAL
ATENÇÃO
SUSPEITO
CRÍTICO

ESTADO DA OCORRÊNCIA:

Representa o processo operacional.

Exemplos:

AGUARDANDO_VALIDACAO
CONFIRMADA
REJEITADA
EM_ATENDIMENTO
RESOLVIDA

IMPORTANTE:

Se o operador rejeitar um alerta, isso NÃO deve necessariamente transformar a telemetria em normal.

Exemplo:

Operador:
REJEITAR

Sistema:

"Ocorrência rejeitada pelo operador."

Mas se os sensores ainda apresentarem comportamento anormal, a telemetria deve continuar como suspeita.

==================================================
8. NORMALIZAÇÃO
==================================================

Após a correção da situação física, a pressão poderá retornar ao comportamento esperado.

O sistema poderá receber uma atualização de normalização.

Exemplo:

"Telemetria normalizada."

IMPORTANTE:

Normalização da telemetria não significa automaticamente que uma ocorrência confirmada está encerrada.

Uma ocorrência confirmada pode continuar:

EM_ATENDIMENTO

e somente depois ser marcada:

RESOLVIDA

==================================================

src/
├── server.ts
├── routes/

├── services/
└── ...

Se já existirem:

reutilizar e melhorar esses componentes.

Evitar colocar toda a regra de negócio no controller.

A regra do chatbot deve permanecer nos services.

==================================================
10. NOVOS MODELOS DE DADOS
==================================================

Caso ainda não existam, preparar interfaces/types para representar uma ocorrência.

Exemplo conceitual:

interface Incidente {
    id: string;
    duto: string;
    trechoProvavel?: string;
    horario: string;
    sensores?: string[];
    status: StatusOcorrencia;
    validacaoHumana?: ValidacaoHumana;
}

Criar enums/types equivalentes, se fizer sentido.

Exemplo:

type StatusOcorrencia =
    | "AGUARDANDO_VALIDACAO"
    | "CONFIRMADA"
    | "REJEITADA"
    | "EM_ATENDIMENTO"
    | "RESOLVIDA";

type ValidacaoHumana =
    | "CONFIRMADA"
    | "REJEITADA";

Não inventar campos que não sejam necessários.

==================================================

Preparar o chatbot para futuramente receber do backend algo semelhante a:

{
    "id": "INC-12345",
    "duto": "D02",
    "trechoProvavel": "D-E",
    "horario": "15:42",
    "sensores": ["D", "E"],
    "criticidade": "alta"

==================================================
12. CONSULTA DE INCIDENTES
==================================================

A funcionalidade anterior de consulta de incidentes pode permanecer como funcionalidade secundária.

Exemplo:

Usuário:

"incidente"

Bot:

"Informe o código do incidente."

Usuário:

"INC-12345"

Bot consulta o backend e retorna os dados disponíveis.

IMPORTANTE:
Essa funcionalidade não é mais o fluxo principal do chatbot.

O fluxo principal é:

detecção → alerta → WhatsApp → validação humana.

==================================================

15. PREPARAÇÃO PARA WHATSAPP REAL
==================================================

A implementação deve ser feita de forma que a integração futura com WhatsApp Business API seja simples.

Separar:

Lógica do chatbot
≠
Transporte da mensagem

Ou seja, o chatbot não deve depender diretamente de uma implementação específica do WhatsApp.

Criar uma abstração/service para envio de mensagem caso isso ainda não exista.

Exemplo conceitual:

Posteriormente essa função será conectada à WhatsApp Business API.

histórico
